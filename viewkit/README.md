# viewkit — 二级视图构建器

> 这是原构想里那件事：**原文是沉积层，模型只读二级视图。**
> 它只造视图，**不计算、不替模型回答**。

## 0. 先定性：这是**注意力管理工程**，不是检索（2026-10-22 用户裁定）

这一条决定后面所有设计，写在最前面：

> **要不要做事，先看目标内容是不是已经落在模型的天然高注意力区。**
> 是 → 系统 **no-op**，什么都不做，整个 viewkit 跳过。
> 不是 → 才启动筛选，把那一段搬进高注意力区。

由此推出三条，和"检索"思路的结论是反的：

| 检索思路（错） | 注意力管理思路（对） |
|---|---|
| 每次提问都要造个视图 | 尾部内容本来就高注意力，**造视图是多此一举** |
| 视图越小越好 | 视图只要**落在舒适预算内**就行；200K token 仍在舒适区 |
| 抓不到就把窗口开大 | 先看是不是**根本不该做**（§2·补2 的续说旁路） |

**所以 viewkit 的真实定义是：只在上下文超过舒适预算、且目标不在高注意力区时才启动的过滤器。**
预算内整份透传，高注意力区直接跳过——两种情况下它都**不产出视图**。

---

## 1. 输入是什么：**上下文文本**，不是 PDF

这一条必须先说清楚，否则边界会一路跑偏：

| 谁负责 | 做什么 |
|---|---|
| **上游 / 模型侧** | PDF→文本、OCR、表格抽取、多模态转写 |
| **本工具** | 拿到**已经在上下文里的文本**，决定"该把哪一小段留给模型" |

所以：

- **不做 PDF 解析**，也不该做——文本到这一步已经是文本了；
- 之前 README 里那些 OCR / PDF 的担忧（`NX 7001`、`0↔O`）**是上游的事**，本工具只在极端情况下兜底；
- 沉积层 = **当前上下文**（对话、工具返回、已解析文档），不是文件系统。

**这一条把问题砍掉一半**：不需要处理解析器，只需要处理"上下文太长、该送哪一段"。

## 1·补 它解决什么

两周实验的核心发现只有一句：

> **模型的失败不在"读不懂"，在"没读到"。** 单事实只要把那一句推到它面前，10/10。

聚合现在在册的读数是：**视图 1/7、全档 2/7**（`results/rep_ds_rep_view_*.json` vs `rep_ds_rep_full_*.json`）。
把输出上限从 40 提到 1500 后，DS 在 130K 全档能枚举全 20 项并正确累加出 **102495**（用 245 token）。

**读数总则**：任何"模型做不到"的结论，先排除是不是我们自己的 `max_tokens` 把输出截断了。
`max_tokens=40` 曾让一批聚合题全部误判为失败。

所以产品形态不是"更聪明的模型"，是**一个知道该把哪一小段推过去的层**。

## 2. 两种视图，不是一种的裁剪

> **默认就是 `turns`**（用户裁定）。不传 `--mode` 走它。

| 模式 | 触发 | 视图内容 | 实测尺寸 |
|---|---|---|---|
| **turns（默认）** | 语料是**对话回合**格式（用户一句 + AI 一段） | **整回合入选，按原文顺序输出**（§2·补2）；目标在尾部时 **`view=None`** | 119 回合语料，r=0.25 → 18/18 |
| lookup | 非回合语料 + 问句指向具体实体（`NX-7001`） | **只含该实体的那一句** | **78 字符** |
| gather | 非回合语料 + 问句在问整体（total / how many） | **该类型的所有实例**（不是 top-k） | 20 条 → **1,662 字符**；5 条 → 414 |
| search | 非回合语料 + 以上都不是 | 句级 BM25（可选 CE 精排） | 207K 语料 → **32 字符视图** |
| auto | 显式传才生效 | **按语料格式判断**：有回合标记 → turns，没有 → 退回一代路由 | — |

一代（lookup / gather / search）是为早期合成语料造的，**判据靠英文正则**
（`ENTITY=[A-Z]{1,3}-\d{3,6}`、`AGG_HINT` 全是 total/how many 等英文词），
中文问句在它们上面基本只剩 `search`。这也是默认必须指向 `turns` 的原因。

**这不是同一个视图的大小差别，是两种不同的视图。**

- lookup：最小窗口。实测 gold 单句（105 字符）即 10/10，2K 视图比所需大近 20 倍；
- gather：**必须全量**。实测把 5 条全放进 3,127 字符视图，聚合从"枚举根本没发生"变成"五项全进加法"（1/5 → 3/5）。

**gather 的关键数字：20 条事实的全部视图只有 1,662 字符——一个 2K 预算装得下整个聚合集合。**

## 2·补 第三种模式：search（打分器）

前两种模式都要求问题里**有可识别的东西**（实体 id 或聚合词）。两者都没有时，走语义检索：

| 模式 | 触发 | 视图 | 实测 |
|---|---|---|---|
| search | 无实体、无聚合词 | BM25 粗筛 20 → CE 精排取 top-1 | 207K 语料 → **32 字符视图**，CE 分 **0.905** |

**实测例子**（`demo/corpus/real_k8s_t2.txt`，200,403 字符）：

```
问：which image does the tensorflow serving deployment use?
视图：image: tensorflow/serving:2.19.0     （32 字符，CE 0.905）
```

这就是原构想里"打分器"的岗位——只是它现在只负责**选句子**，不负责选块。

### ⚠ 单位该选哪个：由语料结构决定，不是由速度决定

| 语料 | 结构 | 正确单位 | 依据 |
|---|---|---|---|
| 硬语料 / 五针（散文混体） | 无分节 | **句** | BM25 recall@5 = 100%，CE@5 把 top-1 从 60% 拉到 100% |
| k8s 配置（`===== FILE:` 分节） | 有分节 | **块（文件）** | 句级下 gold 答案行 **recall@5 = 0/30**——BM25 只找得到文件头 |

**规则**：上下文里有分节标记 → 块；无分节散文 → 句。**这不是调参，是单位定义错误。**

### ⚠ 块级 vs 句级：实测与直觉相反

| 单位 | n | 平均长度 | 耗时 | ms/对（CPU） |
|---|---|---|---|---|
| 句级 | 20 | 24 字符 | 3.84 s | **192** |
| 句级 | 119 | 39 字符 | 26.2 s | 220 |
| **块级** | 20 | 3,557 字符 | **38.3 s** | **1,916** |
| 块级全量 | 45 | 4,452 字符 | 83.9 s | 1,865 |

**块级单位少 97 倍，但每对长 150 倍 → 总成本反而高 ~10 倍。**
"块级更快"不成立：CE 的成本按**字符**走，不按**条数**走。

结论：**块级只适合当 BM25 的粗筛单位（0.01 s，免费），不适合进 CE。**

### ⚠ CE 的隐藏参数：512 token 截断（已实测）

`FlagReranker` 的 `max_length` 默认 `None` → 走内部 collator。实测：

```
块 3,000 字符 / 878 token
全量打分     0.013305
只给前 512 token 打分  0.013305   ← 完全相同（差 0.00e+00）
```

**结论：超过 512 token 的部分根本没进模型。块级 CE 的分数只反映块头。**

这不是"慢"的问题，是**分数不可信**的问题。记录口径：
型号 `bge-reranker-v2-m3`｜实际截断 **512 token**｜硬件 **CPU（Intel64, 8 线程）**｜≈**190 ms/对**

### CE 的成本账（为什么必须两级）

| 测点 | 耗时 |
|---|---|
| 模型加载 | 4.9 s（一次性） |
| CE 20 对 | 1.3 s |
| CE 200 对 | 10.5 s（≈50 ms/对） |
| **全量 5,400 句** | **≈270 s（不可用）** |

所以：**BM25 粗筛 20 → CE 精排**。CE 是可选层（`--ce`），内核仍零依赖。

## 2·补2 turns 模式：对话语料的**主线**（2026-10-21 用户设计）

上下文天然就是「用户一句 + AI 一段」的回合格式。所以单位是**回合**，不是句子：

> **某回合内任何一方相关，就把这一整块搬进去。绝不拆句。**

为什么必须是整块：句子拼贴实测 **0/3**，连续原文切片 39.6K 实测 **3/3**。拆开就死。

### 预算口径是 **token**，不是字符（用户裁定）

200K **token** 仍在注意力舒适区（≈80 万英文字符 / 约 30 万中文字符）。
`est_tokens` 按中文 1.5 字/tok、其他 4 字/tok 估算；装不下整回合就跳过并标 `incomplete`——**绝不拆块**。

**默认预算就是 200K token**（`DEFAULT_BUDGET_TOKENS`，CLI 和 `build_view` 都是）。
不传 `--budget` 不会变成"不限"。实测：119 回合 / 130,717 tok 的语料全量入选；
1.43M tok / 5,000 回合的合成语料被压到 **854 回合 / 200,361 tok**——过滤器这时才真正启动。

**关键推论**：真实语料（130K token）和 513K 字符（≈129K token）的那批语料都**小于 200K 预算**，
所以 viewkit 在它们上面等于整份透传——这解释了为什么"39.6K 和 513K 表现一样"：
不是大小无所谓，是**都在预算内，都等于全量**。

真正超过预算、能让过滤器实转起来的，目前只有合成的三档长对话（415K / 838K / **1.43M** token）。

### 相对预算：悬崖在 0.25 与 0.20 之间

真实语料（GLM 119 回合 / **130,717 tok**；私人会话**不随仓分发**，见 `corpus/DATA_SOURCES.md`）
+ 18 题标注 QA，BM25-only，读数 `results/eval_ratio.json`：

| 比例 r | 预算 tok | 命中 |
|---|---|---|
| 1.000 | 130,717 | 18/18 |
| 0.500 | 65,358 | 18/18 |
| **0.250** | **32,679** | **18/18 ← 悬崖边** |
| 0.200 | 26,143 | 16/18 |
| 0.125 | 16,339 | **17/18**（修掉 × 分词 bug 后） |

建议取 **1/4**，不是 1/5 也不是 1/8。

### 规模不是瓶颈（合成长对话，BM25-only）

| 语料 | r=0.25 | r=0.125 | 造视图耗时 |
|---|---|---|---|
| 415,928 tok / 1,500 回合 | 12/12 | 12/12 | 0.34–0.37 s |
| 838,535 tok / 3,000 回合 | 12/12 | 12/12 | 0.66–0.72 s |
| **1,426,877 tok / 5,000 回合** | **12/12** | **12/12** | **1.10–1.14 s** |

延迟约线性。**1.43M token / 5,000 回合，1/8 预算下 12/12，1.1 秒出视图。**
但必须同读一句：这 12 题全是**事实型 + 唯一 ID**（词面必中）。**它只回答规模，不回答难度**——
真实语料里 aggregate / referent 在 1/8 档会掉。

### ⚠ 续说旁路：整个 viewkit 跳过（2026-10-22）

「继续」「接着说」「Go on」这类短回复，命中 `CONTINUE_WORDS` 后：

```python
return {"mode": "turns", "view": None, "spans": [], "n_blocks": 0,
        "view_tokens_est": 0, "bypass": "passthrough", ...}
```

**不打分、不排序、不切块、不装预算。`view=None`，宿主照原样把对话发过去。**

理由就是 §0 那条：续说要接的内容**本来就在尾部高注意力区**，系统再做任何事都是多余的。

**注意不是"取尾部 N 回合"。** 那仍是系统在产出视图，与 §0 直接冲突——既然目标已在高注意力区，
就不该由我们来决定给几个回合。正确行为是完全不产出，交给宿主原样透传。

实测（119 回合语料，CPU）：

| 路径 | 耗时 |
|---|---|
| 续说旁路（no-op） | **16–19 ms** |
| 正常 BM25 路径 | 114–122 ms |

**预算对旁路无意义**：不产出视图，就没有东西可装，`budget` 传多少都不影响结果。
回归脚本里有一条专门锁死这个性质（`budget=500` 下断言 `view=None`、`tok=0`）。

## 3. 它不做什么

| 不做 | 为什么 |
|---|---|
| 不回答问题 | 回答是模型的事；这一步只负责"把材料摆好" |
| 不做聚合计算 | 见 §6——那是另一条路线，而且是否必要还没定 |
| 不编造缺席 | 实体不在沉积层 → 返回空视图 + `not_found`，由上层拒答 |
| **高注意力区不做任何事** | 见 §0 和 §2·补2——目标已在尾部高注意力区时，`view=None`，不造视图 |

## 5. 用法

```bash
python viewkit.py --corpus doc.txt --ask "What is the entry count for NX-7001?"
python viewkit.py --corpus doc.txt --ask "What is the total of all entry counts?" --json
python viewkit.py --corpus doc.txt --ask "..." --mode gather --budget 2000
python viewkit.py --corpus conv_turns.txt --ask "..." --budget 32000   # 默认 turns
python viewkit.py --corpus conv_turns.txt --budget 32000    # 不给 --ask：Q 自动取末条用户输入
python viewkit.py --corpus conv_turns.txt                   # 预算默认 200K token
python viewkit.py --corpus doc.txt --ask "..." --mode auto  # 非回合语料：按格式判断
python viewkit.py --self-test
```

> ⚠ 非回合语料（针型语料、k8s 配置）**不传 `--mode` 会被强制成 turns** —— 因为默认就是 turns。
> 这批语料请显式传 `--mode auto`（或直接 `--mode lookup/gather/search`）。

不给 `--ask` 时，**Q = 最新一条用户输入信息块**（turns 的设计口径），此时 `--mode` 自动按 `turns` 处理。
`latest_user_turn` 同时认 `user:` / `assistant:` 与 `用户：` / `助手：` 两套标记。

输出（JSON）：

```json
{
  "mode": "gather",
  "view": "Archive NX-7100 ... holds 7505 entries ...\n...",
  "spans": [4330, 4341, ...],
  "chars": 1662,
  "n_facts": 20,
  "truncated": false,
  "note": "全量实例视图（不是 top-k）；截断会发生则显式标注"
}
```

`spans` 指回沉积层的行号——**这是"下钻"的接口**。今天只做到接口，没有做交互。

turns 模式额外返回 `n_blocks` / `view_tokens_est` / `bypass`，两种形态：

```json
{ "mode": "turns", "view": "===== TURN 118 =====\n...", "spans": [117, 118],
  "n_blocks": 2, "view_tokens_est": 2091, "bypass": null }

{ "mode": "turns", "view": null, "spans": [], "n_blocks": 0,
  "view_tokens_est": 0, "bypass": "passthrough" }
```

**`view: null` 不是错误**，是 §0 的定义：目标已在高注意力区，系统不做任何事。宿主照原样发对话。

## 6. 与结算器（aggsettle）的关系：它是另一条路线，且必要性待定

| | 救援视图（本工具） | 结算器（aggsettle） |
|---|---|---|
| 路线 | 修**读取**，模型仍然读 | 绕**读取**，不让模型读 |
| 适用 | 全部任务 | 仅可形式化任务 |
| 状态 | **主线** | **旁支，未证明必要** |

aggsettle 是在免费实验里派生的，不是原构想的一部分。它的前提是"模型做不到"。
这个前提**只在部分条件下成立**：输出上限放开后 DS 在 130K 全档能算出 102495（正确），
但同一档的另外 5 道聚合题只过 1 道，视图档 1/7、全档 2/7。
5 针语料上视图能把枚举从 1/5 拉到 3/5——**视图修的是枚举，不是算术**。

**判定实验待跑**：把 1,662 字符的 gather 视图直接给模型，看它能不能自己聚合。
若能 → 结算器降为可选的校验器；若不能 → 它才挣到位置。

## 6·补 CE 到底值不值：深度 5 的实测

| 语料 | BM25 top-1 | **BM25 + CE@5** | 成本 |
|---|---|---|---|
| 硬语料 20 题 | 12/20 = **60%** | **20/20 = 100%** | 100 对 / 17.8 s ≈ **0.9 s/题** |
| k8s 30 题（gold=答案行） | 0/30 | 0/30 | — **单位选错，见上** |

**CE 在散文语料上把 8 个漏全吃掉，单题 0.9 秒——它挣到了自己的位置。**
但这不是"CE 更好"，是"CE 在**句级 + 散文**这个组合里更好"；换个单位组合就不成立。

**换到 turns（回合级）就不成立了**：40 回合 / 2,207 tok 的一次两级筛选约 **10 秒**（CPU，预热后；
首次含加载约 42 秒）→ **只能离线 / 批处理，不能交互**。所以 turns 模式默认 BM25-only，
CE 走 `--ce` 显式开启。

CE 在这层买的**不是排序**——BM25 的 top-1 通常已经对了——而是**分数尺度**：
BM25 给不出"我有多确定"，CE 给得出（0.994 vs 0.134，7 倍分差）。
低分拒答的闸门因此才有量可依。长回合按 ~512 token 切块取最大分，是近似（任一块相关即整回合入选）。

## 7. 泛化能力：说实话

**代码 342 行 / 16.4KB（+ retriever 137 行 / 5.0KB）。小不是优点，是窄的证据。**

| 路径 | 泛化程度 | 依据 |
|---|---|---|
| lookup（正则 + 形态规则） | **窄**：只认 `NX-7001` 这种"大写字母-数字"形态 | 4/4 自检全在自造语料上 |
| gather（同型实例） | **窄**：假设同类型实体形态一致 | 同上 |
| search（BM25/CE） | **较宽但要实测**：只在 2 个语料上试过 | k8s 那例 CE 0.905 vs 次优 0.004，分差很大 |
| **turns（BM25 整回合）** | **只在 3 个语料上试过**：真实对话 2 份（14 / 119 回合）+ 合成 3 档 | 18 题 18/18@r=0.25；合成 12/12 但**全是事实型题** |

**语料是最大的窄处**：真实对话语料只有 **2 份会话**，标注 QA 只有 **18 题**（非事实型仅 6 道）。
所有比例/悬崖结论都建立在这个量级上，**未做第二语料验证**。

**没有做的事**：真实 PDF 解析、表格、跨段指代（"那个服务"）、多语言、非 ID 型实体名。

**所以正确的说法是**：它是一个**能跑通的骨架**，把"该不该送、送哪一段"这件事显式化了；
不是通用产品。

## 8. 已知缺陷（写出来，不藏）

1. **抽取靠形态规则**，`NX 7001`/`NX–7001`/`NX-7OO1` 这些可逆破坏能救，**末位丢失或改写成描述就救不回**（实测 0/20）；
2. **`spans` 只是行号**，没有做"从答案跳回原文"的交互；
3. **gather 假设同类型实例可用同一形态识别**，现实语料里不一定成立；
4. 归一化踩过坑：早期把 `to 9216` 也合成 `to-9216`，现在只认大写前缀；
5. **CE 只做句子级重排**，没有块级；block 边界靠换行，对 PDF 转文本不友好；
6. **search 模式的阈值没有定**——现在无论分数多低都会返回一句；低分应拒答，但阈值未标定；
7. **paraphrase gap**：问题用了答案里不存在的同义词时 BM25 抓不到。实测两个"漏项"最后都归因到这——
   一个是 `×` 分词 bug（已修），一个是问法用词脱离原文（换原文说法即命中）。
   **这是 BM25 的固有边界，不是题型问题**，任何题型都会中；
8. **`est_tokens` 是估算**（中文 1.5 字/tok、其他 4 字/tok），不是真分词器。预算贴近边界时不可信；
9. **续说词表是手写维护的**（`CONTINUE_WORDS`），漏词会误走检索、收太宽会误跳过。
   误跳过的代价更大——没有视图兜底。未做词表的覆盖度评估；
10. **`view_tokens_est` 比 `budget` 略大**（1.43M 语料实测 200,361 vs 200,000，约 +0.2%）——
    装箱按**单回合**算 `est_tokens`，但输出时回合之间要拼 `\n\n`，这段分隔符没算进预算。量级无害。
